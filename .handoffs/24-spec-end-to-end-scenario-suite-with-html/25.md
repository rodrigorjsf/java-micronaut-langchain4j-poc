## What was built
- One committed weather scenario row (`src/test/resources/evals/scenarios/weather.json`, id `weather-happy-forecast-tomorrow`). The loader reads it from the scenarios directory: files sorted by name, rows kept in file order.
- `ScenarioRunner` sends every turn through `POST /api/chat` on an embedded server using plain `java.net.http`. It then reads the trajectory back from a test-only `RecordingAgentTracer`: the outcome, the skill activations, and each tool call's name, arguments and result.
- Trajectory checks are the expected final `outcome` and each expected tool having been called. Each check carries a reason that a reader can act on.
- `EvalReportRenderer.render(List<ScenarioResult>)` is a pure function that returns one self-contained HTML string: inline CSS, no script, no link, no src. Every string is escaped. Each scenario shows its source, turns, expectation, outcome, activations, tool calls, answer, checks, latency and tokens.
- `ScenarioSuiteEval` (`@Tag("evals")`) runs the committed rows against the real model and writes `eval-report.html` at the repository root in `@AfterAll`, so the report is written even when the eval fails. `eval-report.html` is in `.gitignore`.

## Decisions & deviations
- All scenario code is test code under `src/test/java/.../evals/scenario/`. `RecordingAgentTracer` lives in `testsupport` behind `agentic.test.recording-agent-tracer=true`. `OtelAgentTracer`'s `@Requires(missingBeans=AgentTracer.class)` makes it step aside, and `LangfuseToolListener` feeds the recording tracer.
- Activations are derived from recorded `activate_skill` tool calls, using the `skill_name` argument.
- Dataset file format: each domain file is a bare JSON array. `turns` is an array of strings. `expect.trajectory` = `{outcome, toolsCalled[]}`. Jackson is strict about unknown fields, so later tickets must extend the records when they add fields.
- `dependsOn` is loaded and committed with plain identifiers (`geo-and-weather`, `get_weather`, `open-meteo-forecast`), even though #25's field list omits it. #24's row shape requires it, and ticket 3 will validate it.
- The report path is `${user.dir}/eval-report.html`. Surefire's working directory is the repo root. There is no JUnit extension yet: it is written from the eval's `@AfterAll` because only one test class writes it today.
- The default build does NOT write `eval-report.html`, so a stub run never masquerades as a real report.
- A non-200 from `/api/chat` becomes a failed `request` check carrying the response body. The scenario still appears in the report.
- The eval paces 10 s between scenarios, reusing `TriageGoldenSetEval`'s measured limit, and pins `agentic.observability.capture-content=true` so tool payloads always reach the report.
- Docs: `docs/05-evaluation.md` has a new section, "End-to-end scenarios", with a Mermaid diagram. The README run command and the prompt-change checklist mention the report.
- Only `eval-report.html` was added to `.gitignore`. `retrieval-report.html` belongs to the retrieval ticket.
