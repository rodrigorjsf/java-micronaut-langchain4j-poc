## What was built
- A committed calibration set, `src/test/resources/evals/grader-calibration.json`. It has one entry per rubric criterion, and every labelled row carries `split` (train/dev/test), `pass` (the human label), `critique` and `labelledBy`. The loader rejects invalid rows and names the file, the row and the rule broken.
- `GraderCalibration.measure(set, split, grader)` produces TPR and TNR per criterion and counts UNGRADED rows separately. It refuses the train split. `describe` prints both rates as fractions, and a rate that cannot be computed shows as "n/a".
- `RubricGrader.withFewShot(model, set)` shows the Grader a criterion's train rows, and only those, as few-shot exchanges. `ScenarioSuiteEval` now uses it, so the scenario suite runs the same prompt the calibration measures.
- The recalibration trigger. `CalibrationRecord` holds a `Fingerprint` of three things: the grader model, a SHA-256 of the grader prompt (instructions, question template, response format and train rows), and the agent model. `GraderCalibrationFreshnessTest` runs in the default build and fails, naming each change, whenever the committed record's fingerprint differs from the current configuration.
- `GraderCalibrationEval` (tag `evals`) measures dev and test against the real grader, prints the shortfalls and writes the record for review and commit.
- `shortfalls` enforces the sizing floor: at least 60 rows per criterion, and both labels present in dev and in test.
- Documentation: a "Calibrating the Grader" section in `docs/05-evaluation.md` with tables and a Mermaid diagram, a Calibration set entry in the `CONTEXT.md` glossary, and one line in `README.md`.

## Acceptance criteria
- [x] TPR and TNR are reported separately per criterion. Proved by `GraderCalibrationTest.tprAndTnrPerCriterion` (worked example: TPR 2/3, TNR 1/2), `onlyTheSplitIsGradedAndUngradedIsCountedApart` and `describesEachCriterion`.
- [x] Recalibration is triggered when the grader model, its prompt or the agent model changes. Proved by `CalibrationRecordTest.eachChangeTriggersRecalibration`, `RubricGraderTest.thePromptFingerprintFollowsTheTrainSplitOnly`, and the wiring in `GraderCalibrationFreshnessTest`.
- [x] Grader few-shot examples come only from the train split. Proved by `RubricGraderTest.fewShotExamplesComeOnlyFromTheTrainSplit`, `aCriterionWithoutTrainRowsIsZeroShot` and `GraderCalibrationTest.theTrainSplitIsNeverMeasured`.

## Decisions & deviations
- **The human labels were NOT produced, and the committed set has zero rows.** A model-labelled row would measure the Grader against another model, and an agent cannot supply human labels. Filed as #55 (ready-for-human). The ticket's "What to build" is therefore only partly delivered: the machinery and the ACs are done, the data is not.
- The rubric still never gates. The ticket says "only then may rubric checks gate", but no gating threshold was defined, so none was invented. The docs say this explicitly.
- One rubric criterion counts as one failure mode. "Both classes" means at least one PASS row and one FAIL row in dev and in test. No balance ratio is enforced, because the spec gives no number.
- The record keeps the test-split counts only. Dev results are printed, because dev is for tuning.
- When no record exists, the freshness test passes, since nothing can go stale yet.
- `GraderCalibrationEval` writes the record into `src/test/resources`, so a recalibration shows up as a reviewable diff.
