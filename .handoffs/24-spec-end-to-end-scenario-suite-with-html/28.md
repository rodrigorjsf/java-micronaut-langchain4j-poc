## What was built
- A scenario row can now declare `"upstream": {"catalogueKey": "<key>", "failure": "server-error" | "timeout" | "oversized"}`.
- `ScenarioSuiteEval` runs such a row in its own app context. That one catalogue key's `base-url` points at a failure route of the test `StubApiController`. The model and every other upstream stay real, and the shared context never sees the override. The context is closed after the row.
- `StubApiController` has three new catch-all routes: `/stub/fail/server-error/{+path}` answers 500, `/stub/fail/timeout/{+path}` answers after 3 s, and `/stub/fail/oversized/{+path}` answers 1 MiB of JSON. For the timeout shape, the faked key's timeout drops to 1 s.
- `weather.json` has three new rows, one per shape (`weather-upstream-server-error`, `-timeout`, `-oversized`). They are non-critical and depend on `open-meteo-forecast`.
- `eval-report.html` has a "Faked upstream" row on every scenario, for example "open-meteo-forecast faked: HTTP 500". A row without an override shows "none: every upstream was real".
- An override naming a key outside the catalogue is refused with `IllegalArgumentException`. Without this, it would silently fake nothing while the report said it had.

## Acceptance criteria
- [x] The override is declared by the scenario, not by a global profile. Proved by `ScenarioDatasetTest.anUpstreamFailureRowDeclaresItsOverride` and `aHappyRowFakesNothing`, and by `UpstreamFailureScenarioTest`, which builds its context from the row's `upstream.properties(...)`. In the eval, only the per-row context carries the override.
- [x] Each of the three failure shapes can be selected. Proved by `UpstreamFailureScenarioTest.theDeclaredFailureReachesTheModel` (3 parameterized cases), which checks what the model is handed: "The service is unavailable" for 500 and for timeout, and `[truncated: ...` for oversized.
- [x] The report shows which upstream was faked. Proved by `EvalReportRendererTest.namesTheFakedUpstream`. A keyless `-Pevals` run printed all four "Faked upstream" cells.

## Decisions & deviations
- **"Asserts what the agent tells the user" is partial by design.** The failure rows assert the trajectory: outcome ANSWERED and `get_weather` called. The default-build test checks the failure text the tool door hands the model. There is no answer-text check yet because answer checks are #26 (`expect.answer`). The real model's reply is shown in the report. `docs/05-evaluation.md` names this gap.
- The runner branches on `upstream != null`, not on `kind`. Consistency validation between the two belongs to #30. I added it as a comment on #30.
- The timeout shape overrides the faked key's `timeout` to PT1S. Otherwise the turn would wait out the real 6 s budget twice, because of the retry.
- The oversized body is 1 MiB, above the largest ceiling in the catalogue (524288 bytes), so any key pointed there is truncated at its own `max-response-bytes`.
- Rows use new Portuguese inputs (Curitiba, Recife, Porto Alegre). Each row is its own conversation.
- The `FailureShape` JSON name is also its stub route (`@JsonValue`), and the report's description is derived from the timeout value.

## Notes for dependent tickets
- `Scenario` gained a last record component, `UpstreamFailure upstream` (nullable). New constructors need the extra argument.
- `Scenario.UpstreamFailure(catalogueKey, FailureShape failure)` with `properties(URI stubServer, Set<String> catalogue)` returns a `Map<String,Object>` to merge into the app config. `describe()` returns the report text.
- `Scenario.FailureShape`: SERVER_ERROR, TIMEOUT, OVERSIZED (JSON: `server-error`, `timeout`, `oversized`).
- `ScenarioSuiteEval.run(Scenario)` picks the shared or the per-row faked context. Repetitions (#27) should call it N times; each call starts a fresh faked context.
- #26: the upstream-failure rows should gain `expect.answer` checks (for example, the answer says the data is unavailable and invents no value).
- #30: validate `kind == "upstream-failure"` iff `upstream != null`.
