## What was built
- Each scenario now runs N times, 3 by default. Set N with `-Dscenarios.repetitions=N`. Every repetition starts a fresh conversation.
- A `critical` scenario fails the eval if any repetition that ran failed. A non-critical scenario reports PASSED, FLAKY or FAILED and never fails the eval.
- A repetition the model provider rate-limited is SKIPPED. The endpoint returns an opaque HTTP 500, so the runner reads the cause from the recording tracer: the last failed GENERATION whose error passes `FailoverTriageJudge.isRateLimit`.
- If every repetition of the run was skipped, the eval is aborted (JUnit assumption) instead of passing.
- `eval-report.html` shows "Repetition i of N" for each run. Its summary lists passed scenarios, gate failures, flaky scenarios (`id (2/3)`), skipped repetitions, total tokens and the estimated cost.
- The estimated cost is the sum of the `total` that `CostCalculator` already attaches to every model call through `LangfuseChatModelListener`. There is no new price table. Calls to unpriced models are counted and shown, never priced at zero.

## Decisions & deviations
- **"critical requires 3/3" means all repetitions that ran.** SKIPPED repetitions count neither way, so a critical scenario at 2 passed + 1 skipped passes. The spec says both "3/3" and "rate-limited runs are SKIPPED, not failed". Counting a skip as a failure would contradict the second, so I read the rule this way. It is documented in `docs/05-evaluation.md`.
- A critical scenario at 2/3 is listed both as a gate failure and as flaky. Flaky means passes are between 1 and executed−1, following the spec's "scenarios with 1–2 of 3".
- `FailoverTriageJudge.isRateLimit` went from package-private to `public`. That is the only `src/main` change, and it only widens visibility. I made it to reuse the existing classifier instead of duplicating it. No new seam was added.
- `ScriptedChatModel` now calls `ChatModelListener.onError` before rethrowing a scripted failure, the way real providers do. Without this, no default-build test could produce a failed GENERATION.
- `RecordingAgentTracer.Recorded` gained `usage`, `cost` and `error` components.
- A skipped repetition keeps the cost of the calls made before the quota error. Its tokens stay 0, because the endpoint reported none.
- The summary labels the two sources: tokens as reported by `/api/chat`, cost from every model call the tracer saw (judge and sub-agents included).
- `ScenarioRuns.Status` was renamed from `Verdict`, which is the triage glossary term in CONTEXT.md.
- `EvalReportRenderer.render` now takes `List<ScenarioRuns>` instead of `List<ScenarioResult>`.

## Learnings
- `ScriptedChatModel` did not call `onError`. Scripted failures were invisible to tracing until now.

## Notes for dependent tickets

- New answer or grounding checks go into each repetition's `checks`. The renderer shows them per repetition.
