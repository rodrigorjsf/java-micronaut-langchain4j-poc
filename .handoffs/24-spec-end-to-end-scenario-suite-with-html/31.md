## What was built
- A new model role, `grader`, lives in `application.yml` (`agentic.llm.models.grader`: OpenAI `gpt-4o-mini`, temperature 0). It is built by the existing `ChatModelRegistry`. A new cross-role rule, `ModelRoleValidator.validateAcrossRoles`, stops the registry from being built when `grader` has the same provider and model as `agent`, and the error message names both.
- A scenario row can carry `expect.rubric`, a list of plain-language criteria. The two `weather.json` rows that have one are the happy row and the server-error row.
- `RubricGrader` (test sources) makes one grader call per criterion and reads back `{"pass", "critique"}`. Each criterion becomes a `RubricVerdict`: PASS or FAIL, plus the critique. It is UNGRADED when the grader throws or replies with something that is not a verdict.
- The verdicts live in `ScenarioResult.rubric`, which is kept separate from `checks`. As a result they never affect `passed()`, the status or the critical gate.
- `eval-report.html` shows the rubric criteria for each scenario and the verdicts with critiques for each repetition, all labelled uncalibrated. The summary has a rubric tally line.
- `ScenarioSuiteEval` gets the grader from the registry through `forRole("grader")`.

## Acceptance criteria
- [x] The grader is resolved through the existing registry, and building fails clearly if it equals the agent model. Proved by `ChatModelRegistryTest.theShippedGraderIsAModelOtherThanTheAgent` and `aGraderConfiguredToTheAgentsModelFailsAtStartup`. See the decisions below for what "startup" means here.
- [x] Verdicts are binary per criterion, with a short critique shown in the report. Proved by `EvalReportRendererTest.rendersTheRubricAsReportOnly`, which also checks HTML escaping and the uncalibrated label.
- [x] A failing rubric never fails the eval. Proved in the default build with a stub grader by `ScenarioRunnerTest.aFailingRubricNeverFailsTheEval`: the committed row is critical, the grader returns FAIL, and the row still gets `passed()`, PASSED and `failsGate()==false`. `anUnreadableVerdictIsUngraded` covers a grader reply that is not a verdict.

## Decisions & deviations
- The grader is configured in the shipped `application.yml`, not only in the eval's configuration, so "resolved through the existing registry" holds everywhere. The app never calls it. Its credential (OpenAI) is already required by `judge-fallback`.
- The equality rule compares provider and model name, ignoring case and surrounding whitespace. Temperature does not count. It runs only when both roles are configured.
- "Startup fails" means the registry refuses to be built. I measured that the registry is lazy: an embedded server started with an invalid grader config starts anyway. The eval resolves the registry before its first scenario, so a bad grader fails the eval at once. The eager-startup gap was already there before this ticket and is filed as #51. The docs and the yml comment were reworded so they do not overclaim.
- A third value, `UNGRADED`, exists alongside PASS and FAIL. It means "no verdict", so a grader error never reads as FAIL. Any verdict the grader actually returns is binary.
- Grader calls are recorded by the same tracer, so each repetition's cost includes grading. The cost label in the report says so. Latency does not include grading.
- The critique hides exception messages and shows only the type. An unreadable reply is echoed truncated to 200 characters.
- Rubric criteria were also added to the upstream server-error row, because polite failure handling is the main use of a rubric.

## Learnings
- A Micronaut `@Singleton` `ChatModelRegistry` is lazy, so "fails at startup" tests need `ApplicationContext.run(EmbeddedServer...)`, not `getBean`.

## Notes for dependent tickets
- `Scenario.Expectation(trajectory, answer, rubric)`. The 2-arg constructor is kept, and `rubric` defaults to an empty list.
- `RubricGrader(ChatModel)` with `grade(criteria, turns, answer) -> List<RubricVerdict>`. Use `RubricGrader.NONE` when no grader is wanted.
- `RubricVerdict(criterion, Verdict{PASS, FAIL, UNGRADED}, critique)`.
- `ScenarioResult` has a 10th component, `rubric`, plus `withRubric(verdicts, cost)`. The 8-arg constructor is kept.
- `ScenarioRunner(URI, tracer, links, grader)`. The 3-arg constructor means no grader.
- In a stub context, script the grader with `StubChatModelRegistry.model("grader")`.
